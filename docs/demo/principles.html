01 · step 1 the naive way

Run the same sum twice.
Get two answers.

Same deposit, same interest formula, two runs an hour apart. They should match to the cent. They don't — because the formula quietly reaches outside its inputs: the clock, the database, a dash of randomness.

one formula · two runs · hidden inputs

interest = principal × rate(now()) × db.dayCount() × jitter()

run B · today 10:22
interest = principal × rate(now()) × db.dayCount() × jitter()
€ —
 
 
each run re-reads the hidden inputs — so the euros drift
01 · step 2 the idea

A pure function
can't surprise you.

A side effect is anything code does beyond turning its arguments into an answer — reading the clock, hitting a database, rolling a die. A pure function has none: its result depends only on what you pass in. So the same inputs always give the same output.

the intuition A written recipe is pure — same ingredients, same steps, same cake, every kitchen, every day. A chef who improvises to taste is impure: delicious, maybe, but you can't reproduce it. A bank needs the recipe.
The fix is mechanical: take the three hidden inputs and lift them out to arguments — pass rate and days in. Same arguments → same euros, forever. (that's the code on the next slide)
PRINCIPLE 01

A pure core,
a thin shell.

The shell touches the world — loads, appends, publishes. The core only sees data and returns events.

"No clock, no I/O, no randomness" isn't a slogan — it means every input is an explicit argument. Same arguments → same money, every time.

The slogan, and the
code underneath it.

slogan → reality

decide(state, command) → events is the teaching shorthand. There's no single decide(). The pure fold is a handler; the command→events decider lives in each family's Application layer, never in the generic engine.

interface IEventHandler<TState, TEvent> HandlerResult<TState> Apply(TState s, TEvent e); // (state, event) → state — pure
engine/src/Babelstone.Engine/Handlers.cs:39 · decider: families/term-deposit/…/TermDepositDecider
enforced, not promised

Purity isn't a code-review hope. Roslyn analysers BENG001/002/003 fail the build if a handler reads the clock, does I/O, or uses randomness.

"But you need today's rate — that's non-deterministic." Right: so the shell resolves it before the decider runs and stamps it into the event — DepositConstituted carries rate_sheet_version_id. The clock is an injected TimeProvider, read only at append. Every non-deterministic input becomes recorded data; the fold over it stays pure.

02 · step 2 the idea

Don't overwrite. Append.

Never change a stored fact; never delete one. To record interest you add a new fact — "InterestPaid +€139". The balance isn't stored — it's computed by replaying the facts in order. That replay-and-add-up is the fold: a running total over the events.

2InterestPaid+€139.00
3InterestPaid+€139.00
fold(events) → position
€0.00
nothing overwritten · full history kept
the balance is derived, never stored — so it can always be rebuilt
PRINCIPLE 02

State is just fold(events).

So replay is deterministic: two lanes, same log, different speeds — both fold to a byte-identical state hash. Timing doesn't matter; the function is pure.

03 · step 2 the idea

Make the engine
not care.

Flip who knows what. The spine — API, store, bus, projections, maths — knows nothing about any product. A family is a sealed module that plugs in and brings its own four things: events, folds, lifecycle, decider.

the intuition A power strip doesn't know what you'll plug into it — kettle, lamp, charger. It exposes one socket shape and stays unchanged as you add appliances. The engine is the strip; a product family is an appliance. Adding one touches nothing that already worked.
New code, yes. Surgery on the core, never. The next slide makes that a number: +1 family = one wiring line, zero engine edits.

04 · step 1 the naive way

Put the name in the event.
Lose control of it.

A bus is the shared pipe every service reads from — copied, cached and backed up on purpose, so nothing is lost. Put a customer's name and NIF in the event and that durability works against you: the person fans out everywhere.

04 · step 2 the idea

Send a reference.
Keep the person in a vault.

Two moves. The bus carries only a reference — a meaningless one-way token for "which customer". The real name and NIF are encrypted in a vault inside the engine, opened only when a screen or a report truly needs them.

the intuition Each customer's data lives in a locked box with exactly one key. To forget them you don't chase every box across every backup — you destroy that one key, and every copy of the box, everywhere, becomes a brick no one can ever open. That's crypto-shredding.
The non-personal facts — amount, term — aren't encrypted, so the books stay readable after erasure. One key dies; the person is gone; the accounting survives.
PRINCIPLE 04

No PII on the bus.
Forget by shredding a key.

The bus carries a reference, never the person. PII is encrypted and resolved only inside the engine boundary.

GDPR erasure isn't a hunt across every topic and backup. Shred one key → every copy, everywhere, is undecryptable at once.

04 · deep dive OpenBao, transit keys, the erasure event

The locked box,
spelled out.

what actually travels

PII fields in the payload are ciphertext. Even the "which subject" reference is a salted one-way pseudonym (an HMAC), not the raw id — so the bus reference itself can't be reversed.

ADR-PC-004 §P2 · Amendment A2
the vault

OpenBao (Vault-compatible) as a per-subject transit key store — a deliberate, documented exception to the hand-rolled-core rule. Encryption happens at the boundary in AppendAsync; decryption only on display/report paths. Structural fields stay cleartext and queryable.

ADR-PC-004 §Decision · AggregateRuntime.AppendAsync (protector.ProtectAsync)
erasure, exactly

IPiiKeyStore.DestroyKeyAsync(subject) on the transit engine → all ciphertext under that key is unrecoverable. A PersonalDataErasureRequested event records the act; the audit trail survives.

Residual risk, on the record: key-store backups may hold the destroyed key until retention rolls off — truly-complete erasure needs backup-rolloff coordination (ADR-PC-004 §P5).

05 · step 2 the idea

Write the decision down.
Make changing it loud.

An ADR — Architectural Decision Record — is a short, dated, numbered file stating one decision and why. The rule (ADR-PC-020 §D3): you may diverge from an Accepted decision, but only on the record — a change that contradicts one must carry a dated amendment in the same pull request.

the asymmetry that does the work Changing your mind is fine. Changing it quietly is not. The record is never allowed to fall out of step with the code — so six months later the docs still tell the truth, and review starts from the decision, not from guessing.
Divergence is allowed. Silent divergence is blocked. The next slide is the gate that enforces it.

05 · deep dive three layers · amend vs supersede

What actually stops
the silent commit.

three enforcement layers

1 · local hook — adr-immutability.sh warns when you edit an Accepted Decision in place (advisory; CI is authoritative).

2 · CI PR-body gate — adr-governance.yml hard-fails a PR whose body omits the "ADRs touched/honoured" section.

3 · conformance subagent — reads the diff against the governing ADRs and proposes an amend/supersede for contradictions no mechanical gate sees.

ADR-PC-020 §P1 · §P3 · §D3 · .github/workflows/adr-governance.yml
amend vs supersede

Amend — append a dated *Revised YYYY-MM-DD:* block; the core decision stands. For refinements.

Supersede — write a new ADR, flip the old one to Superseded by …, git mv it into adrs/retired/, sweep the links. For a decision that actually reverses.

§P9 workflow: a flag → fix the code or amend/supersede in the same PR → name it in the PR body. Review starts from the decision.

PRINCIPLE 06

The balance is a fold,
not a column.

Every product is an account — a stream of movements. The spendable balance is never stored: it's accounting − Σ holds, folded from events on every read.

The number a legacy core mutates in place — and gets wrong — we refuse to store at all. A hold lowers it; a freeze blocks it; a rebuild reproduces it to the cent.

The coda · built for the messy parts

The same rigor, where the
real world gets messy.

Scale · resumable

Bulk operations

A regulator forces a change across every affected account. The runner freezes a target universe, drains it idempotently, isolates per-item failures, and resumes mid-run after a crash with exact counts.

ADR-PC-035 · BULK_OP_REGISTER_DRAIN_COMPLETE · Live
Legal · compliance

Holds & freezes

A court garnishment makes funds unspendable; an AML freeze blocks debits and names why in the refusal. First-class replayable facts — not a flag on a row.

ADR-PC-041 · FREEZE_GATES_AUTHORIZATION · Live
Privacy

Erase by shredding

Forget a customer by destroying one key — every encrypted copy, everywhere, becomes unreadable at once. Right-to-be-forgotten as a single audited act.

ADR-PC-004 · crypto-shredding · principle 04
Integrity

Reconciliation & drills

The read models are checked against the log daily and alarm on drift; a cold rebuild must reproduce every belief — a fast-but-wrong cache is the worst failure mode, so it's gated.

ADR-PC-002 · rebuild drill · ACCOUNT_BALANCE_IS_A_FOLD
Time

Expiry without clocks

No engine fact is ever manufactured from the wall-clock. Holds and freezes lapse when an operator appends a fact off a projection horizon — so replay stays deterministic, forever.

ADR-PC-023 · projection-derived signals
Audit

Bitemporal truth

Every event records when it happened and when we learned it — separately (valid-time vs transaction-time), so a backdated correction never rewrites what the books said at the time.

Why it composes

Six choices. One property.

A pure core makes replay deterministic. Determinism makes the log the truth. A generic spine lets families plug into that truth. The PII boundary keeps it lawful. The drift gate keeps the record honest — and the balance is a fold, so the money is only ever as true as the log.
