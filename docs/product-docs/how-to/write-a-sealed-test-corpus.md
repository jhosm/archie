# How to write a sealed test corpus for a pack

A pack's **sealed test corpus** is its regression evidence — the "the engine plus
this pack do what the brief claims" proof that BdP supervision and DORA-style due
diligence ask to see ([ADR-PC-007 §P5](../../product-management/product_concepts/adrs/ADR-PC-007-signed-yaml-oci-pack.md)).
This guide tells you what the corpus is, the one file you author, the one file you
must never touch, and how to run it.

The single most important rule, stated up front so you do not get it wrong: you
**hand-author the inputs**; the **expected events are generated**. Author the wrong
file and you have defeated the entire point of the corpus.

## What the corpus is, in two files

The corpus lives in `test-corpus/` inside the pack and is exactly two files:

| File | You author it? | What it holds |
|---|---|---|
| [`canonical-instances.yaml`](../../../packs/pt.2026.1/test-corpus/canonical-instances.yaml) | **Yes — hand-authored INPUTS** | One canonical instance per interest shape: the variant, principal, constitution date, and the resolved TAN — all *inputs*, never computed results. |
| [`expected-events.yaml`](../../../packs/pt.2026.1/test-corpus/expected-events.yaml) | **No — GENERATED, never authored** | The event sequence the engine produces from those inputs. Produced by running the engine over the inputs and committing the result. |

The split is the whole design: if a human wrote the expected events, the corpus
would just be checking that two human-written files agree, which proves nothing about
the engine. Because the expected side is *generated by the engine*, the corpus
catches the engine silently changing behaviour — that is what makes it evidence
([ADR-PC-007 §P5](../../product-management/product_concepts/adrs/ADR-PC-007-signed-yaml-oci-pack.md)).

## The file you author: `canonical-instances.yaml`

Each entry is one regulator-meaningful scenario. Every field is an **input**:

```yaml
# illustrative — the authoritative worked set is in pt.2026.1's corpus
tests:
  - test_id: pt_dpz_12m_simple_with_irs
    pack: pt.2026.1
    variant_id: dpz_pt_12m_juros_venc
    principal_cents: 1000000        # €10,000.00
    constituted_at: 2026-01-15
    rate_basis_points: 300          # 3.00% TAN (resolved input)
```

A few points that trip people up:

- **`rate_basis_points` is an input here, not pack data.** The live engine *resolves*
  the rate from the rate sheet at constitution
  ([ADR-PC-008](../../product-management/product_concepts/adrs/ADR-PC-008-rate-sheet-storage-and-deploy-api.md)).
  The corpus pins it per instance so the regression is **deterministic** even though
  the real rate sheet moves on its own fast cadence. It is *not* pack-authored
  rate-sheet data, and it is *not* a derived figure (TANB/TANL/TAE) — those are
  engine-computed and live nowhere in the pack. The corpus numbers are illustrative
  sealed-corpus inputs, not regulated figures.
- **Cover every interest shape.** The `pt.2026.1` corpus carries one instance per
  shape the family schema offers — AT_MATURITY single-coupon, periodic-monthly,
  periodic-quarterly, advance/`juros antecipados`, a banded early-termination
  schedule, and a partial-withdrawal case. A new shape in your pack means a new
  canonical instance.
- **`test_id` is the stable handle.** Name it for the scenario; it is how a failure
  is reported and how a regulator references the case.

To extend the corpus: add a `tests:` entry for the new shape, leave
`expected-events.yaml` alone, and let the generation step (below) fill in the
expected side.

## The file you must never author: `expected-events.yaml`

`expected-events.yaml` opens with a `DO NOT HAND-AUTHOR` banner, and it means it.
The publish gate **regenerates** it by running the engine over
`canonical-instances.yaml`, so a hand-edited expected file cannot land — the corpus
cannot silently drift
([ADR-PC-007 §P5](../../product-management/product_concepts/adrs/ADR-PC-007-signed-yaml-oci-pack.md)).
Today it is an intentional **empty placeholder** (`expected: []`) because the
generation step is still being built (see the deferral below).

## How to run it

The corpus is exercised by **depth 5** of the validator, the engine simulation.
Depths 1–4 (`make pack-validate`) do **not** run it; depth 5 is a separate CI gate.

```sh
# Depths 1–4 — your pack's YAML soundness. Does NOT run the corpus.
make pack-validate PACK=pt.2026.1
```

When you run `make pack-validate`, depth 5 shows up as a **logged skip**, never a
pass:

```
  skip          depth-5 corpus: expected-events.yaml empty (generation pending, C.3)
```

Read that `skip` as exactly that — work that has not run, not work that passed. A
corpus file that is *present but unparseable* is a hard failure, not a skip: the
validator will not let a corrupted evidence file go green. The depth definitions and
budgets are in
[ADR-PC-006 §Context and §P4](../../product-management/product_concepts/adrs/ADR-PC-006-cue-schema-language.md);
[validate a pack locally](./validate-a-pack-locally.md) covers reading the depth-5
skip in context.

## Honest deferral: depth-5 gates the event SEQUENCE, not the full payload (yet)

This is the part to be straight about, because the corpus is regulator-facing and
overclaiming what it checks would be the wrong kind of confidence. The depth-5 gate
landed in two increments, and **only the first has shipped**
([ADR-PC-006 Amendment A1/A2](../../product-management/product_concepts/adrs/ADR-PC-006-cue-schema-language.md)):

- **A1 — shipped today.** Depth-5 loads the committed pack, drives every canonical
  instance through the engine's hand-rolled append/replay substrate (constitute →
  intermediate coupons for periodic shapes → mature, all by explicit command),
  cold-replays each stream, and asserts the produced **`family.EventType` sequence**
  matches the documented per-interest-shape lifecycle. So what is gated today is the
  *shape of the lifecycle* — that the right kinds of events fire in the right order
  — within the depth-5 time budget.
- **A2 — deferred.** The **byte-level** `expected-events.yaml` comparison — checking
  every field of every event payload — is **not** done yet. Generating and comparing
  the full per-event payload corpus is store-side work that exceeds the first
  increment, so `expected-events.yaml` stays the logged-skip empty placeholder until
  it lands. Until then, depth-5 proves the event *sequence*, not the full *payload*.

In one line: **the corpus gates the event sequence now; the full-payload round-trip
follows.** Do not read a green depth-5 as "every field of every event is checked" —
it checks the lifecycle shape, and the placeholder corpus is honestly skipped rather
than falsely passed.

## Why this matters to you as a config author

- **You touch one file: `canonical-instances.yaml`.** Add an instance per new
  interest shape; the inputs are yours.
- **You never touch `expected-events.yaml`.** It is generated; editing it is defeated
  by the regeneration gate and undermines the evidence.
- **A depth-5 `skip` is not a pass.** Treat it as pending work. And remember that
  even once depth-5 runs, today it gates the event *sequence*, not the full payload.
