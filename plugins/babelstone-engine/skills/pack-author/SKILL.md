# pack-author — scaffold and publish a regulatory pack

A **pack** is the versioned, jurisdiction-scoped vocabulary the engine resolves at
constitution and pins per instance for life ([ADR-PC-007](docs/product-management/product_concepts/adrs/ADR-PC-007-signed-yaml-oci-pack.md),
[ADR-PC-006](docs/product-management/product_concepts/adrs/ADR-PC-006-cue-schema-language.md)).
It is **declarative data, not executable code** — signed, version-pinned regulatory
evidence. The canonical form is **auditor-readable YAML**; CUE appears only as
constraint schemas.

## Step 1 — Identity and naming

Packs live under [`/packs`](packs/README.md), named `pt.YYYY.N` (jurisdiction · year ·
sequence). `pack_version` is **immutable once published** — a change is a new version,
never an edit. No PII ever goes in a pack (market/regulatory constants only).

## Step 2 — Scaffold the ADR-PC-007 §P1 layout

One OCI artefact, one tar layer:

```
pack/
  pack.yaml                 # manifest: pack_id, pack_version, namespace, publisher,
                            #   publish_date, schema_version, dependencies.engine_compatible_versions, pins
  schemas/                  # CUE constraint schemas (the ONLY .cue files)
    term-deposit.cue
    common.cue
  primitives/               # pack-bound primitives the schemas reference (YAML)
    day-count.yaml
    tax.yaml
    fgd.yaml
  parameters/
    constants.yaml          # pack-level constants (max_consumer_rate_bps, fgd_ceiling_eur, …)
  rate-sheet-refs/
    deposits-pt.yaml        # version-pinned refs to ADR-PC-008 rate sheets
  test-corpus/              # sealed regression evidence (YAML)
    canonical-instances.yaml
    expected-events.yaml    # GENERATED by the engine — never hand-authored (Step 4)
  README.md                 # human-readable pack-version changelog
```

**Data is YAML** (`pack.yaml`, `primitives/`, `parameters/`, `rate-sheet-refs/`,
`test-corpus/`) — the canonical, `cat`+`diff`-able auditor form. **Constraints are
`.cue`** (`schemas/`). Authors write YAML; engineers/pack-team own the `.cue` files.

## Step 3 — Validate: `pack-validate` depths 1–4 (CUE over the YAML data)

`pack-validate` is the single static Go binary embedding `cuelang.org/go`
([ADR-PC-006 §P2](docs/product-management/product_concepts/adrs/ADR-PC-006-cue-schema-language.md));
it exposes depths 1–4 as subcommands and emits a JSON diagnostics array
(`{depth, path, kind, message, pos}`). Depth-3 pack compliance is, in effect,
`cue vet primitives/ parameters/ schemas/*.cue` — CUE ingests the YAML as data and
unifies it against the constraints. Run depths 1–4 over the scaffolded data and fix
every diagnostic before signing.

> Note: `/pack-validate` is a skeleton today (no binary built yet). Until it ships, the
> depth-1–4 step is authored but cannot execute; do not sign/publish an unvalidated
> pack. Build order: the Go binary (`/pack-validate`) precedes a real publish.

## Step 4 — Depth-5 sealed-corpus simulation (engine substrate, not CUE)

`expected-events.yaml` is **generated** by appending `canonical-instances.yaml` through
the engine's hand-rolled `append` path into a Testcontainers PostgreSQL fixture,
rebuilding the projection, and asserting ([ADR-PC-007 §P5](docs/product-management/product_concepts/adrs/ADR-PC-007-signed-yaml-oci-pack.md),
[ADR-PC-006 §P4](docs/product-management/product_concepts/adrs/ADR-PC-006-cue-schema-language.md)).
Commit the generated file; never hand-author it (the corpus must not silently drift).

> Note: depth-5 needs the engine, which is unbuilt. Until then, scaffold
> `canonical-instances.yaml` and leave `expected-events.yaml` to the first engine-backed
> publish.

## Step 5 — Sign and publish (cosign → oras), pull by digest

Per [ADR-PC-007 §P2](docs/product-management/product_concepts/adrs/ADR-PC-007-signed-yaml-oci-pack.md):

1. `cosign sign` — keyless Sigstore OIDC (engine-team identity in v1; bank-internal OIDC
   in production). The signature **attests depths 1–4 passed in CI** — verified
   signature ⇒ already-validated.
2. `oras push` to a dedicated registry repo (e.g. `babelstone-packs/pt-deposit`) with
   media type `application/vnd.babelstone.pack.v1+yaml`.
3. The engine **pulls by digest (sha256), never by tag**, and verifies the signature at
   load (fail-loud). Pack repos need keep-forever retention (regulatory artefact store).

## Step 6 — Pinning

Every event carries `pack_version` in its envelope ([ADR-PC-001 §P1](docs/product-management/product_concepts/adrs/ADR-PC-001-event-store-technology.md));
a `pack_versions` table maps `(pack_id, pack_version) → OCI digest + signature digest`
([ADR-PC-007 §P3](docs/product-management/product_concepts/adrs/ADR-PC-007-signed-yaml-oci-pack.md)).
An instance keeps its `pack_version` for life until an explicit `PackVersionMigrated`
event — the engine never silently re-resolves.

## Guardrails

- **No PII in a pack** — ever. Packs are market/regulatory constants.
- **`pack_version` is immutable** once published — revise = new version.
- **YAML is canonical**; `.cue` is constraints only. Don't make CUE the source of truth
  for values (that inverts the auditor-readability property ADR-PC-007 chose A for).
- **Don't sign an unvalidated pack** — depths 1–4 must pass first (the signature *is* the
  attestation).
- `expected-events.yaml` is generated, never authored.
- Pack-format/manifest changes are **forward-only/additive** (same discipline as event
  schemas); a removal/re-type needs a new pack-format major version with parallel publish.
